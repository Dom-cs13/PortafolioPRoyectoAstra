ASTRA — Referencia del Compilador

Versión: 1.0 (en desarrollo) · Compilador para simulación de biosferas planetarias

1. Introducción y propósito

ASTRA es un lenguaje de dominio específico (DSL) y un compilador optimizador diseñado para modelar, analizar y ejecutar biosferas complejas. Permite definir planetas, atmósferas, cuerpos de agua y formas de vida, así como establecer reglas de evolución, cálculos y reportes. El compilador valida semántica, unidades físicas y reglas ecológicas, transformando descripciones de alto nivel en simulaciones deterministas.

El proyecto incluye un IDE completo (BioSphereIDE) con editor, resaltado de sintaxis, detección de errores en tiempo real, tabla de tokens, consola de salida y visualizador de árbol sintáctico.

2. Sintaxis del lenguaje

2.1 Estructura general

inicio
    simulacion {
        planeta { ... }
        atmosfera { ... }
        agua { ... }
        vida { ... }
        // funciones y otras sentencias
    }
fin

Bloques obligatorios: planeta, atmosfera, agua. vida es opcional.

2.3 Tipos de datos

  • Números: enteros o decimales (ej. 42, 3.1416, 5.97e24, -10)
  • Textos: entre comillas dobles (ej. "Hola mundo")
  • Booleanos: verdadero, falso
  • Listas: secuencias homogéneas, ej. [1, 2, 3], ["a","b"]
  • Nulo: nulo (para variables sin valor asignado)

2.4 Operadores

  • Aritméticos: + - * / ^ (potencia)
  • Comparación: == != < > <= >=
  • Lógicos: y (AND), o (OR)

2.5 Unidades físicas (opcionales)

Se permiten las siguientes unidades después de un número: km, m, g, kg, atm, ppm, Sv, %, °C, h, s, M🜨, R🜨, AU, K, kPa. Ejemplo: temperatura = 25 °C;

El analizador semántico verifica que en sumas y restas las unidades sean compatibles, y que el exponente de una potencia no tenga unidad.

2.6 Sentencias de control

  • Asignación: identificador = expresión;
  • Condicional: si (condición) { ... } sino { ... } (el bloque sino es opcional)
  • Bucle mientras: mientras (condición) { ... }
  • Mostrar (salida en consola): mostrar(expresión); o mostrar expresión;
  • Reporte (estadística): reporte(expresión);
  • Función: funcion nombre(param1, param2) { ... } (las funciones pueden usar retorno = expresión; para devolver valor)
  • Llamada a función: nombre(argumento1, argumento2);

4. Gramática formal (EBNF)

programa         = "inicio", bloqueSimulacion, "fin" ;
bloqueSimulacion = "simulacion", "{", { sentencia }, "}" ;
sentencia        = bloquePlaneta | bloqueAtmosfera | bloqueAgua | bloqueVida
                 | asignacion | mostrar | reporte | if | while | definicionFuncion
                 | expresionSentencia ;
bloquePlaneta    = "planeta", "{", { sentencia }, "}" ;
bloqueAtmosfera  = "atmosfera", "{", { sentencia }, "}" ;
bloqueAgua       = "agua", "{", { sentencia }, "}" ;
bloqueVida       = "vida", "{", { sentencia }, "}" ;
asignacion       = identificador, "=", valor, ";" ;
mostrar          = "mostrar", [ "(", valor, ")" ], ";" ;
reporte          = "reporte", [ "(", valor, ")" ], ";" ;
if               = "si", "(", condicion, ")", "{", { sentencia }, "}", [ "sino", "{", { sentencia }, "}" ] ;
while            = "mientras", "(", condicion, ")", "{", { sentencia }, "}" ;
definicionFuncion= "funcion", identificador, "(", [ listaParametros ], ")", "{", { sentencia }, "}" ;
valor            = expresion | booleano | cadena | lista | nulo ;
expresion        = termino, { ("+" | "-"), termino } ;
termino          = potencia, { ("*" | "/"), potencia } ;
potencia         = factor, [ "^", potencia ] ;
factor           = numero | identificador | "(", expresion, ")" | llamadaFuncion | "-", factor ;
condicion        = valor, [ ("<"|">"|"<="|">="|"=="|"!="), valor ], { ("y"|"o"), condicion } ;
identificador    = letra, { letra | digito | "_" } ;
numero           = digito, { digito }, [ ".", { digito } ], [ "e", [ "+" | "-" ], digito, { digito } ] ;
cadena           = '"', { carácter - '"' }, '"' ;
lista            = "[", [ valor, { ",", valor } ], "]" ;
nulo             = "nulo" ;
booleano         = "verdadero" | "falso" ;

5. Fases del compilador (detalle técnico)

5.1 Analizador léxico (Lexer)

El lexer convierte el código fuente en una secuencia de tokens utilizando expresiones regulares. Reconoce palabras reservadas (case-sensitive, minúsculas), identificadores, números (enteros, decimales, notación científica), cadenas, operadores y símbolos. Además, detecta errores léxicos:

  • Identificador inválido: comienza con número, ej. 123abc
  • Carácter ilegal: cualquier carácter no definido (ej. @, $, #, &, ?, |, \\, ~, `)
  • Cadena sin cerrar: falta la comilla de cierre al final de la línea

Los errores léxicos se muestran en la consola y se subrayan en el editor con una línea ondulada roja.

5.2 Analizador sintáctico (Parser)

El parser construye un Árbol de Sintaxis Abstracta (AST) siguiendo la gramática LL(1). Valida la estructura global (presencia de inicio y fin), el balance de llaves, el uso correcto de punto y coma, y las reglas de precedencia de operadores. Si encuentra un error, reporta la ubicación exacta y el token esperado.

Ejemplos de errores sintácticos:

  • Falta de ; al final de una sentencia
  • Falta de { después de planeta
  • Uso incorrecto de si sin paréntesis alrededor de la condición
  • Expresiones mal formadas, ej. (5 + sin cerrar

5.3 Analizador semántico

Esta fase recorre el AST y aplica reglas semánticas robustas para garantizar la total coherencia física e informática del programa. Incluye:

  • Tabla de Símbolos de Ámbitos Anidados: Se implementa a través de una pila de ámbitos (scopes stack). Cada bloque de código (simulacion, planeta, if, mientras, funciones) crea un nivel de ámbito local que hereda y sobreescribe variables de los ámbitos ancestros. Cada símbolo almacena su nombre, tipo estricto, valor, ámbito, línea de declaración y unidad física.
  • Detección de Variables No Declaradas: No se permite el uso de ningún identificador que no haya sido inicializado previamente en un ámbito accesible (error SEM-001).
  • Inferencia y Compatibilidad de Tipos: Verifica la compatibilidad en operaciones relacionales y aritméticas (por ejemplo, prohibiendo sumas de cadenas de texto con números decimales, SEM-014).
  • Validación estricta de Unidades Físicas: Admite unidades opcionales como km, m, kg, atm, ppm, °C, h, s, M🜨, R🜨, AU. El analizador semántico valida que las operaciones aritméticas de suma y resta se realicen únicamente entre variables con unidades compatibles (error SEM-030) y que los exponentes en potencias carezcan de unidad (error SEM-031).
  • Variables Obligatorias por Bloque: El validador exige la presencia de variables físicas requeridas para inicializar el simulador:
    • planeta requiere: masa (numérica) y radio (numérica) (error SEM-041).
    • atmosfera requiere: presion (numérica) y co2 (numérica) (error SEM-041).
    • agua requiere: estado_liquido (booleana) (error SEM-041).
  • Verificación de Funciones: Comprueba firmas de funciones, asegurando que las llamadas coincidan con el número exacto de argumentos y rechazando definiciones duplicadas (error SEM-002).

5.4 Tabla de símbolos (estructura)

La tabla de símbolos se implementa con una pila de ámbitos. Cada ámbito es un diccionario nombre → símbolo. Las operaciones principales:

  • PushScope(name) – entra a un nuevo ámbito
  • PopScope() – sale del ámbito actual
  • LookUp(name) – busca el símbolo en el ámbito actual y ancestros
  • AddSymbol(sym) – añade un símbolo en el ámbito actual
  • UpdateSymbol(name, newSym, level) – actualiza un símbolo en un nivel específico

La información almacenada permite la verificación semántica y es utilizada durante la ejecución para obtener valores de variables.

5.5 Ejecución / simulación (Intérprete)

Una vez superadas todas las fases de compilación estática, el motor de ASTRA ejecuta el código fuente a través del Intérprete. Este recorre el árbol sintáctico (AST) validado ejecutando sentencias lineales, resolviendo asignaciones, bifurcaciones condicionales (si/sino), bucles iterativos (mientras), invocaciones de funciones locales y comandos de salida (mostrar y reporte) para emitir resultados lógicos y físicos.

Ejemplo 1: Simulación básica con condicional

inicio
simulacion {
    planeta { masa = 1000 kg; radio = 100 km; }

    vida {
        temperatura = 30;

    }
}
fin

        funcion cuadrado(x) {

10. Conexión en tiempo real con Godot 4 y Shaders en la GPU

El compilador ASTRA implementa una integración en tiempo real sumamente potente y única con el motor gráfico Godot 4, permitiendo visualizar los mundos simulados en 3D interactivo al instante tras cada compilación exitosa en el BioSphereIDE.

10.1 Incrustación de Ventana (Win32 P/Invoke)

El IDE desarrollado en C# / Windows Forms aprovecha llamadas nativas de la API de Windows mediante interoperabilidad (P/Invoke) para incrustar el visualizador 3D dentro de su propio panel de simulación de forma transparente:

  • SetParent: Reparenta la ventana de Godot (visualizador_astra.exe) para que sea hija del panel del IDE.
  • SetWindowLong con GWL_STYLE: Quita dinámicamente los bordes nativos, la barra de título (WS_CAPTION), el borde grueso de redimensionamiento (WS_THICKFRAME) y los menús para lograr una apariencia integrada e impecable.
  • MoveWindow: Modifica el tamaño y posición de la ventana del simulador para ajustarse al 100% del contenedor de Windows Forms, reaccionando en tiempo real al evento Resize del panel.

10.2 Sincronización JSON y FileSystemWatcher

La comunicación de parámetros físicos y astrobiológicos se realiza de forma asíncrona e instantánea:

  1. Filtro DTO (Data Transfer Object): En C#, la clase PlanetaParametros mapea las variables extraídas del bloque planeta, atmosfera, y agua en el AST compilado.
  2. Escritura Temp: Tras una compilación libre de errores, el IDE serializa este objeto a JSON y lo guarda en %TEMP%\astra_planeta.json.
  3. Recepción en Godot: El script de Godot astra_watcher.gd contiene un monitor de cambios de archivo. Al notar el cambio en el archivo JSON, lee y parsea los parámetros y actualiza directamente las propiedades expuestas (@export) en el nodo Planet en tiempo de ejecución.

10.3 Renderizado Procedural en Shaders de GPU

Una vez asignados los parámetros al planeta, Godot propaga las variables físicas a tres Shaders personalizados programados en GLSL/GDScript de forma instantánea:

  • Shader de Terreno (terrain.gdshader): Utiliza algoritmos de ruido procedural (Fractional Brownian Motion - FBM) para modelar montañas, cordilleras y valles. Si la tectonic_activity supera 0.7 y la planet_temp supera los 100°C, calcula fallas tectónicas iluminadas mediante emisión de luz que simulan magma incandescente. Si hay hierro (composition_iron > 0.5), el terreno adquiere texturas oscuras y rojizas de óxido basáltico y mayor especularidad.
  • Shader Atmosférico y Rayleigh (atmosphere.gdshader): Simula de forma realista la dispersión de la luz. Si domina el Metano (atm_methane), tiñe la atmósfera de cian profundo y esmeralda brillante. Si domina el CO2 (atm_co2), el Rayleigh-Mie scattering se desvía a tonos ocre, amarillo y naranja quemado. Si predomina el Nitrógeno/Oxígeno (atm_o2_n2 > 0.7), se mantiene azul celeste translúcido.
  • Shader de Nubes (clouds.gdshader): Genera nubes procedurales cuya densidad se regula por la atm_pressure. Si el periodo de rotación es inferior a 12 horas, las nubes sufren un estiramiento horizontal debido al viento inducido.

10.4 Comportamientos Físicos y Termodinámicos Avanzados

El simulador reacciona dinámicamente según la combinación de variables:

  • Hielo y Evaporación: Si planet_temp < 0°C, congela progresivamente el relieve y océanos convirtiéndolos en hielo azulado. Si planet_temp > 100°C, se evapora el agua líquida secando los mares y activando emisión térmica/magma si se acerca a 400°C.
  • Oblatidad Planetaria: Si el rotation_period_hours < 12h y la planet_mass > 5.0, el motor deforma la escala del planeta (scale.y = 0.85) para simular el achatamiento en los polos provocado por la fuerza centrífuga de la rotación.
  • Gigante Gaseoso: Si la masa planetaria supera 5.0 masas terrestres, el planeta activa automáticamente una textura de nubes ultradensas y oculta su relieve sólido.
  • Tidal Locking (Acoplamiento de Marea): Si la distancia orbital es muy corta (star_distance_au < 0.2) y el periodo de rotación es lento, el ciclo día/noche se bloquea; un hemisferio permanece quemado de forma perpetua mientras el otro se congela.
  • Criterio de Viabilidad Biológica: La vegetación (tonalidad verde #228B22) solo florece si la temperatura superficial se sitúa entre 10°C y 40°C y hay un mínimo de agua líquida del 10% (planet_water > 0.1), validando las estrictas reglas biológicas del compilador.
